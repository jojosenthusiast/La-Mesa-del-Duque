# v1.6.0 — Slice 6: División por Ítems y Tableside

## Resumen ejecutivo

La versión 1.6.0 agrega la división de cuenta por ítems individuales, el caso de uso más complejo del flujo de cobro. Un mesero puede ahora asignar cada línea del pedido a una cuenta específica, incluso dividiendo cantidades parciales (4 cervezas → 2 para Juan, 2 para María). El total de cada cuenta se computa dinámicamente a partir de los ítems asignados, no de una división aritmética externa. Este slice también introduce la vista Tableside, una interfaz tablet-optimizada que permite a los meseros tomar pedidos desde la mesa del cliente con sincronización en tiempo real con el POS principal.

La página Tableside es una SPA (Single Page Application) JavaScript que replica la funcionalidad del POS pero optimizada para pantallas táctiles grandes, con envío incremental a cocina y navegación por gestos.

## Impacto funcional

- **División por ítems**: cada línea del pedido asignable a cuenta 1, 2, 3, etc.
- **División parcial**: 4 cervezas se pueden dividir 2+2; el sistema crea 2 líneas de `CuentaDetalle`
- **Total computado**: al agregar/quitar ítems, el total de la cuenta se recalcula automáticamente
- **Modo selector**: el mesero elige "Partes iguales" (automático) o "Por ítems" (manual)
- **Tableside**: página `/Operaciones/Pedidos/Tableside` optimizada para tablet/iPad
- **Incremental send**: en tableside, el mesero envía ítems a cocina uno por uno o en batch
- **Sync POS↔Tableside**: cambios en tableside se reflejan en el POS principal en tiempo real (SignalR)
- **Touch-optimized**: botones grandes, gestos de swipe, sin hover states

## Impacto técnico

- Nuevo namespace `LaMesaDelDuque.Dominio.Entidades`:
  - `CuentaDetalle`: Id, CuentaId, DetallePedidoId, CantidadAsignada, PrecioUnitario (snapshot al momento de asignar)
- Modificado `Cuenta`:
  - `Total` ahora es propiedad computada: `Detalles.Sum(d => d.CantidadAsignada × d.PrecioUnitario)`
  - No tiene setter público; protege integridad del total
- Modificado `Pedido`:
  - `CrearCuentasConItems(Dictionary<int, List<(Guid detalleId, int cantidad)>> asignaciones)`: crea cuentas con ítems pre-asignados
- Modificado `PedidosServicio`:
  - `CrearCuentasConItemsAsync(Guid pedidoId, Dictionary<...> asignaciones)`: orquesta creación de cuentas + detalles
  - Validación: cantidad asignada no puede exceder cantidad del detalle; suma de asignaciones = cantidad total
- Nuevas páginas Razor:
  - `Pages/Operaciones/Pedidos/Tableside.cshtml`: layout sin navbar, botones grandes, grid táctil
  - `Tableside.cshtml.cs`: `[Authorize(Roles = "Mesero,Encargado,Administrador")]`
- Nuevo archivo `wwwroot/js/tableside.js`:
  - SPA con estado local (carrito, mesa seleccionada)
  - Comunicación con backend vía fetch API
  - SignalR para recibir confirmación de envío a cocina
  - localStorage compartido con POS (`LMDD-Tableside-{mesaId}`)

### Decisión arquitectónica relevante

Se eligió **SPA JavaScript para Tableside** en lugar de Razor Pages interactivas porque:

1. **Touch UX**: la navegación por postbacks de Razor Pages introduce latencia perceptible en tablets; una SPA evita recargas completas.
2. **Offline parcial**: el estado del carrito se guarda en localStorage; si la conexión se pierde momentáneamente, el mesero no pierde el pedido en construcción.
3. **Reutilización**: `tableside.js` comparte lógica con `pos.js` (selección de producto, cálculo de totales) pero con rendering táctil diferente.

La alternativa (Razor Pages con HTMX o Blazor) habría requerido más infraestructura o runtime más pesado para un beneficio marginal en este contexto.

## Riesgos y mitigaciones

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| Tableside y POS pueden conflictear en mismo pedido | Media | SignalR sync + localStorage compartido; notificación de edición concurrente |
| División parcial compleja para mesero | Baja | UI visual con pool de ítems; cantidad ajustable con +/- |
| Total computado lento en pedidos grandes | Baja | Computación en memoria; máximo ~50 ítems por pedido |
