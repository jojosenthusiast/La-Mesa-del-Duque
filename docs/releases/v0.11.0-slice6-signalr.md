# v0.11.0 — Slice 6: Notificaciones en tiempo real con SignalR

## Resumen ejecutivo

La línea 0.11.0 agrega notificaciones en tiempo real al flujo de pedidos mediante SignalR. Este slice crea la infraestructura de comunicación server→client para que la UI y otros sistemas conectados reciban eventos cuando un pedido es creado, cambia de estado o es cancelado, sin necesidad de polling.

El diseño usa una abstracción `INotificadorPedidos` en la capa de aplicación para mantener la separación de capas, con una implementación concreta `SignalRNotificadorPedidos` en la capa web. Las notificaciones son fire-and-forget: si SignalR falla, el flujo principal del pedido no se ve afectado.

---

## Cambios principales

| Área | Cambio | Resultado |
|------|--------|-----------|
| Contrato de notificación | `INotificadorPedidos` en `Aplicacion/Notificaciones/` | La capa de aplicación define qué notificar sin depender de SignalR |
| Hub | `PedidosHub` en `Web/Hubs/` | Los clientes se conectan a `/hubs/pedidos` para recibir eventos |
| Implementación | `SignalRNotificadorPedidos` en `Web/Servicios/` | Traduce llamadas de `INotificadorPedidos` a invocaciones de SignalR |
| Integración | `PedidosServicio` recibe `INotificadorPedidos` por constructor | Emite notificaciones después de cada operación exitosa: crear, cambiar estado, cancelar |
| Test doubles | `NotificadorPedidosSpy` + `NotificadorPedidosNulo` | Permite verificar emisión de notificaciones sin depender de SignalR en tests |
| DI | `Program.cs`: `AddSignalR()` + `MapHub<PedidosHub>()` + registro de `INotificadorPedidos` | Infraestructura lista para que cualquier cliente SignalR se conecte |

---

## Impacto funcional

- **UI / clientes conectados**: reciben notificaciones en tiempo real cuando:
  - Se crea un nuevo pedido (`PedidoCreado` con ID y estado Pendiente)
  - Un pedido cambia de estado (`Pendiente→EnPreparacion`, `EnPreparacion→Pagado`)
  - Un pedido es cancelado (`PedidoCancelado`)
- **Fire-and-forget**: si el hub de SignalR no está disponible, el pedido se procesa igual. Las notificaciones se pierden silenciosamente (logueadas, no propagadas).
- **Sin auth en MVP**: cualquier cliente conectado al hub recibe todos los eventos. La restricción por rol se agrega en un slice futuro.

## Impacto técnico

- Nuevo namespace `LaMesaDelDuque.Aplicacion.Notificaciones`:
  - `INotificadorPedidos` con 3 métodos
- Nuevo namespace `LaMesaDelDuque.Web.Hubs`:
  - `PedidosHub` (hereda de `Hub`, sin métodos públicos — solo push server→client)
- Nuevo namespace `LaMesaDelDuque.Web.Servicios`:
  - `SignalRNotificadorPedidos` (implementa `INotificadorPedidos`, inyecta `IHubContext<PedidosHub>`)
- Modificado `PedidosServicio`:
  - Nuevo parámetro `INotificadorPedidos notificador` en constructor
  - Llamadas a `notificador.NotificarPedidoCreadoAsync()` en `CrearPedidoAsync`
  - Llamadas a `notificador.NotificarEstadoCambiadoAsync()` en `MarcarEnPreparacionAsync` y `PagarPedidoAsync`
  - Llamadas a `notificador.NotificarPedidoCanceladoAsync()` en `CancelarPedidoAsync`
- Modificado `Program.cs`:
  - `builder.Services.AddSignalR()`
  - `app.MapHub<PedidosHub>("/hubs/pedidos")`
  - `builder.Services.AddScoped<INotificadorPedidos, SignalRNotificadorPedidos>()`
- SignalR es parte del shared framework de ASP.NET Core 8 — no se agregó ningún paquete NuGet

### Decisión arquitectónica relevante

Se eligió **inyección directa de `INotificadorPedidos`** en `PedidosServicio` en lugar de un bus de eventos (MediatR) porque:

1. **Simplicidad**: el código base actual no tiene infraestructura de eventos de dominio. Agregar MediatR para un solo caso de uso (notificaciones) es sobre-ingeniería.
2. **Testabilidad**: la interfaz permite un spy manual en tests sin depender de un contenedor de eventos.
3. **Capa correcta**: `INotificadorPedidos` vive en Aplicacion, donde pertenece la orquestación de side-effects. La implementación concreta (SignalR) vive en Web, manteniendo la dependencia en la dirección correcta.

Si en el futuro surgen más casos de uso que requieran eventos de dominio (auditoría, invalidación de caché, webhooks), se evaluará migrar a MediatR. Por ahora, la interfaz directa es suficiente y más fácil de razonar.

## Riesgos y mitigaciones

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| Sin auth en el hub — cualquier cliente recibe todos los eventos | Media | Scope MVP; se agrega auth por rol en slice futuro |
| Notificaciones perdidas si SignalR falla | Baja | Fire-and-forget por diseño; clientes deben re-sincronizar estado al reconectar |
| Sin mecanismo de reconexión del lado servidor | Baja | SignalR maneja reconexión del lado cliente automáticamente |
