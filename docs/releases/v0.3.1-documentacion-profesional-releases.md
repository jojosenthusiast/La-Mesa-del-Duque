# v0.3.1 — Documentación Profesional de Releases

## Resumen ejecutivo

La versión 0.3.1 formaliza el estándar de documentación profesional de releases para La Mesa del Duque. A partir de esta versión, Release Please conserva su función mecánica de versionado, changelog y etiquetado, mientras que la documentación curada vive en `docs/releases/` con contexto ejecutivo, impacto, verificación, riesgos y próximos pasos.

Este cambio no agrega funcionalidad de negocio. Su valor está en elevar la trazabilidad, la claridad histórica y la calidad de comunicación técnica del proyecto.

---

## Cambios principales

| Área | Cambio | Resultado |
|------|--------|-----------|
| Documentación curada | Se agregan páginas profesionales para `v0.2.0` y `v0.3.0` | Cada release relevante tiene explicación estratégica, técnica y verificable |
| Definición de hecho | Se agrega un criterio obligatorio para documentación de releases relevantes | La calidad documental queda integrada al proceso de entrega |
| Plantilla de PR | Se agrega un checklist para confirmar documentación curada | Cada PR significativo obliga a revisar si requiere página de release |
| Changelog | Se mejora la sección `0.3.1` con resumen y detalles accionables | La salida de Release Please deja de ser el único punto de lectura |

---

## Impacto funcional

- **Stakeholders**: pueden entender qué valor entrega cada versión sin leer commits ni diffs.
- **Equipo técnico**: cuenta con una fuente estable para explicar decisiones, límites, riesgos y próximos pasos.
- **Revisores**: tienen un criterio explícito para exigir documentación de release cuando un cambio sea significativo.

---

## Impacto técnico

- No modifica código de aplicación.
- No modifica proyectos .NET ni dependencias NuGet.
- No introduce cambios de base de datos, migraciones ni configuración de despliegue.
- Añade una capa documental encima del changelog automatizado para que la historia del proyecto sea comprensible a largo plazo.

## Riesgos, límites y decisiones

### Riesgos identificados

- **Duplicidad documental**: `CHANGELOG.md` y `docs/releases/` pueden divergir si no se actualizan juntos. Mitigación: la definición de hecho y la plantilla de PR ahora obligan a revisar la documentación curada.
- **Release Please sigue siendo mecánico**: la herramienta seguirá generando texto básico si los commits son pobres. Mitigación: los PRs relevantes deben usar títulos y cuerpos de squash commit con `Summary` y `Details`.

### Límites de esta versión

- No reemplaza Release Please.
- No automatiza la generación de documentación curada.
- No reescribe releases ya publicados en GitHub; documenta el estándar de aquí en adelante.

### Decisiones relevantes

| Decisión | Justificación |
|----------|---------------|
| Mantener Release Please | Sigue siendo útil para versionado, tags y changelog básico |
| Crear `docs/releases/` | Permite documentación de alta calidad sin depender de la salida limitada del bot |
| Exigir documentación solo para releases relevantes | Evita burocracia para cambios triviales |
| Mejorar cuerpos de squash commit | Alimenta mejor al changelog automatizado y conserva trazabilidad técnica |

---

## Próximos pasos

1. Usar cuerpos de squash commit con secciones `Summary` y `Details` en PRs relevantes.
2. Crear o actualizar una página en `docs/releases/` antes de fusionar cambios que generen una versión importante.
3. Mantener Release Please para automatizar versiones, pero tratar sus PRs como contabilidad de release, no como documentación final.
4. Evaluar más adelante si Release Drafter aporta valor adicional para generar notas de GitHub más ricas desde PRs.
