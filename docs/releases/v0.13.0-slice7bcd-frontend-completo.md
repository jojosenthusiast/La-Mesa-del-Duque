# v0.13.0 — Slices 7b+7c+7d: Frontend operativo completo del Sprint 1

## Resumen ejecutivo

La línea 0.13.0 completa el **frontend operativo** del Sprint 1, entregando las cuatro consolas de trabajo necesarias para la operación del restaurante: Productos (mantenimiento), Usuarios (administración), Mesas (estado del salón) y POS/Pedidos (terminal de servicio). Todos los módulos consumen los contratos backend estables y siguen el sistema de diseño operacional establecido en 0.12.0.

El sistema ya puede ser operado end-to-end por el staff: login, gestión de catálogo, control de salón, captura de pedidos y notificaciones en tiempo real.

---

## Cambios principales

| Área | Cambio | Resultado |
|------|--------|-----------|
| Productos | Consola de mantenimiento con tabla densa, filtros y CRUD | El encargado puede crear, editar, desactivar y buscar productos |
| Usuarios | Administración protegida por rol con creación y desactivación | El administrador controla quién accede al sistema |
| Mesas | Grid de estado del salón con badges de resumen | El personal ve el estado de todas las mesas de un vistazo |
| POS/Pedidos | Terminal split workspace con catálogo y panel de orden | El mesero/cajero captura pedidos bajo presión con total siempre visible |
| SignalR JS | Cliente que se conecta a `/hubs/pedidos` | Notificaciones en tiempo real de pedidos como toasts |
| Polish | Empty states, toasts, confirmación destructiva, accessibility | Experiencia consistente y segura en todos los módulos |

---

## Impacto funcional

- **Encargado de catálogo**: puede filtrar por categoría/estado, editar inline, desactivar productos con feedback claro si hay pedidos activos.
- **Administrador**: puede crear usuarios, asignarles rol, y desactivarlos. El enlace "Usuarios" solo aparece en la nav para admins.
- **Personal de salón**: puede ver el estado de todas las mesas instantáneamente, cambiar estado con un click y crear/editar mesas.
- **Cajero/Mesero**: puede capturar pedidos con split workspace (productos a la izquierda, orden a la derecha), ver el total siempre, y ejecutar transiciones de estado (preparar, pagar, cancelar) con botones semánticos.
- **Todos los roles**: reciben notificaciones en tiempo real cuando un pedido cambia de estado.

### Decisión arquitectónica relevante

Se optó por **Razor Pages puras** con PageModels delgados que orquestan los servicios de aplicación existentes, sin introducir frameworks frontend pesados (Angular, React, etc.). Esto mantiene la stack simple: Bootstrap 5 + CSS operacional + JS ligero + SignalR para tiempo real. El POS usa un split workspace con formularios POST estándar, no una SPA. Si la complejidad de interacción crece en el futuro, se evaluará agregar componentes Blazor incrementales.
