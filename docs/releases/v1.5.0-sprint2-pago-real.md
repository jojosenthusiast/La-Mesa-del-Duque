# v1.5.0 — Slice 5: Arquitectura de Pago Real

## Resumen ejecutivo

La versión 1.5.0 introduce la arquitectura de pago real del sistema, transformando el pedido de una entidad monolítica en un flujo de sub-cuentas (`Cuenta`) y transacciones inmutables (`Pago`). Un pedido puede ahora dividirse en múltiples cuentas (por ejemplo, 4 comensales = 4 cuentas con total igual), cada una con su propio método de pago, propina y auditoría de usuario. El estado `EnCobro` permite que el sistema diferencie entre "pedido en preparación" y "pedido listo para pagar".

Este slice también prepara el terreno para el trabajo concurrente de múltiples meseros: se introduce `RowVersion` en la entidad `Cuenta` para manejar concurrencia optimista, y SignalR se extiende con métodos de grupo para que otros terminales sepan cuándo un mesero se une o sale de un pedido en cobro.

## Impacto funcional

- **Sub-cuentas**: un pedido de $400 entre 4 comensales genera 4 cuentas de $100 cada una
- **Pago por cuenta**: cada comensal paga su cuenta individual con método independiente (efectivo, tarjeta, etc.)
- **Propina por cuenta**: cada cuenta lleva su propia propina (10%, 15%, 20%, custom)
- **Estado EnCobro**: el mesero marca "solicitar cuenta" → pedido pasa a EnCobro → sistema genera cuentas
- **Auditoría**: cada `Cuenta` y `Pago` registra `UsuarioId` del mesero que operó
- **Concurrencia**: dos meseros no pueden pagar la misma cuenta simultáneamente (RowVersion + retry)
- **SignalR sync**: cuando un mesero abre el cobro, otros terminales ven que está "en cobro" en tiempo real

## Impacto técnico

- Nuevo namespace `LaMesaDelDuque.Dominio.Entidades`:
  - `Cuenta`: Id, PedidoId, Total, PropinaMonto, MetodoPago, EstadoCuenta (Abierta, Pagada, Cancelada), UsuarioId, RowVersion (timestamp)
  - `Pago`: Id, CuentaId, Monto, Metodo (Efectivo, Tarjeta, Transferencia), PropinaMonto, UsuarioId, FechaPago
  - `EstadoPedido.EnCobro` agregado al enum existente
- Modificado `Pedido`:
  - Método `CrearCuentas(int cantidad)`: genera N cuentas con `Total = Pedido.Total / cantidad`
  - Transición `MarcarEnCobro()`: cambia estado a `EnCobro` si está `EnPreparacion`
- Modificado `PedidosServicio`:
  - `CrearCuentasAsync(Guid pedidoId, int cantidad)`: orquesta generación y persistencia
  - `PagarCuentaAsync(Guid cuentaId, MetodoPago metodo, decimal propina, Guid usuarioId)`: crea `Pago`, marca cuenta como `Pagada`, verifica si todas las cuentas del pedido están pagadas → transiciona a `Pagado`
- Nuevo repositorio `ICuentaRepositorio` / `CuentaRepositorio`:
  - CRUD básico + `ObtenerPorPedidoAsync(Guid pedidoId)`
- SignalR:
  - `UnirseAPedido(Guid pedidoId)`: agrega conexión al grupo del pedido
  - `SalirDePedido(Guid pedidoId)`: remueve conexión del grupo
  - Notificación `PedidoEnCobro` a grupo cuando se generan cuentas
- EF Migrations:
  - `Sprint2_PagoReal`: tablas `Cuentas` y `Pagos` con FK a `Pedidos` y `Usuarios`

### Decisión arquitectónica relevante

Se eligió **concurrencia optimista (`RowVersion`)** en lugar de pesimista (bloqueos) porque:

1. **Escalabilidad**: no mantiene conexiones de DB bloqueadas; tolera alta concurrencia de meseros.
2. **Simplicidad**: el patrón de retry con exponencial backoff es estándar en .NET y fácil de testear.
3. **Frecuencia baja**: colisiones de pago son raras (dos meseros pagando la misma cuenta al mismo segundo); el costo de retry ocasional es menor que el de locks permanentes.

La alternativa (bloqueo pesimista con `SELECT FOR UPDATE`) habría requerido manejo explícito de timeouts y deadlock, complicando el servicio sin beneficio real.

## Riesgos y mitigaciones

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| División en partes iguales no cubre todos los casos | Media | Slice 6 agregará división por ítems asignables |
| RowVersion requiere manejo de excepción en toda la app | Baja | Excepción `DbUpdateConcurrencyException` atrapada y retriada en servicio |
| SignalR grupos por pedido pueden escalar mal | Baja | Grupos se limpian al salir; pedidos pagados no generan tráfico |
