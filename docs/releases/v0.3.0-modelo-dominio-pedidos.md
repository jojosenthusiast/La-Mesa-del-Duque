# v0.3.0 — Modelo de Dominio de Pedidos

**Fecha de publicación**: 2 de mayo de 2026
**Rama base**: `main` (desde `feature/arquitectura-dominio-base`)
**Commit de referencia**: `2510e69` — `feat(dominio): implementar base del modelo de pedidos`

---

## Resumen ejecutivo

La versión 0.3.0 entrega la base del modelo de dominio del sistema de pedidos de La Mesa del Duque. Se implementaron cinco entidades de negocio con sus invariantes, dos enumeraciones, una excepción de dominio personalizada y 47 pruebas unitarias que validan todas las reglas de negocio. Se adoptó el enfoque *domain-first*: el modelo de dominio se construye y verifica completamente antes de implementar persistencia o infraestructura. Esta versión sienta las reglas de negocio inmutables que gobernarán toda funcionalidad futura de pedidos, productos y mesas.

## Cambios principales

### Entidades del dominio

| Entidad | Propiedades clave | Reglas de negocio |
|---------|------------------|-------------------|
| **CategoriaProducto** | `Id` (Guid), `Nombre` (string), `Activo` (bool) | Nombre obligatorio y no vacío. Se crea activa por defecto. |
| **Producto** | `Id` (Guid), `Nombre` (string), `Precio` (decimal ≥ 0), `Categoria` (CategoriaProducto), `Activo` (bool) | Nombre obligatorio. Precio ≥ 0. Debe pertenecer a una categoría no nula. Se crea activo por defecto. |
| **Mesa** | `Id` (Guid), `Numero` (int > 0), `Capacidad` (int > 0), `Estado` (EstadoMesa) | Número y capacidad > 0. Se crea en estado `Disponible`. |
| **DetallePedido** | `Producto` (Producto), `Cantidad` (int > 0), `PrecioUnitario` (decimal ≥ 0), `Subtotal` (decimal, calculado) | Producto no nulo. Cantidad > 0. Precio ≥ 0. Subtotal = Cantidad × PrecioUnitario (solo lectura). |
| **Pedido** | `Id` (Guid), `Mesa` (Mesa), `Estado` (EstadoPedido), `Detalles` (IReadOnlyList\<DetallePedido\>), `Total` (decimal, calculado) | Mesa no nula. Se crea `Abierto`. No se pueden agregar detalles si está `Cerrado`. No se puede cerrar sin detalles ni cerrar dos veces. Total = suma de subtotales (solo lectura). |

| **EstadoPedido** | `Abierto` (acepta modificaciones), `Cerrado` (finalizado, inmutable) |

### Excepción de dominio

- **ReglaDominioException**: excepción base que hereda de `System.Exception`. Se lanza ante cualquier violación de invariante del dominio (precio negativo, nombre vacío, cerrar pedido sin detalles, etc.).

## Impacto funcional

- **Dominio blindado**: Las reglas de negocio están codificadas en las entidades mediante setters privados y métodos de mutación con validación. Es imposible crear un `Pedido` sin mesa, un `Producto` con precio negativo, o cerrar un pedido vacío desde cualquier capa de la aplicación.
- **Lenguaje ubicuo**: Todos los nombres (entidades, propiedades, enumeraciones, excepciones) están en español y reflejan fielmente el dominio del restaurante, eliminando la fricción cognitiva entre el código y el negocio.
- **Sin dependencias externas**: El proyecto `LaMesaDelDuque.Dominio` no referencia ningún paquete NuGet ni otras capas del sistema. Es puro C# con la biblioteca estándar.

---

## Impacto técnico

- **Arquitectura en capas respetada**: Dominio no depende de Infraestructura ni de Web. Este principio se mantiene estrictamente y está verificado por las pruebas unitarias (no requieren base de datos ni contenedor web).
- **Encapsulamiento estricto**: Todas las propiedades tienen setters privados. La mutación del estado se realiza exclusivamente mediante métodos con nombre de negocio (`AgregarDetalle()`, `Cerrar()`, `Activar()`, `Desactivar()`), no mediante asignación directa de propiedades.
- **Colecciones inmutables**: `Pedido.Detalles` expone `IReadOnlyList<DetallePedido>`, impidiendo que código externo modifique la colección sin pasar por las validaciones de dominio.
- **Preparación conceptual para persistencia**: El dominio se mantiene libre de dependencias de EF Core. Los constructores y mapeos requeridos por persistencia se definirán en la capa de infraestructura cuando se implemente el `DbContext`, evitando contaminar el modelo de dominio antes de tiempo.
- **Sin migraciones de base de datos**: Esta versión es puramente de dominio. Las migraciones de EF Core se implementarán en una versión futura cuando se defina el `DbContext` y los mapeos.

## Riesgos, límites y decisiones

### Riesgos identificados

- **Cantidad insuficiente de pruebas**: 47 pruebas cubren los invariantes básicos, pero no cubren combinaciones complejas de estados ni escenarios de concurrencia. **Mitigación**: se agregarán pruebas de integración y escenarios más complejos en versiones futuras.
- **Evolución del modelo**: cambios en las reglas de negocio requerirán modificar las entidades y sus pruebas. La documentación (`modelo-dominio.md`) debe mantenerse sincronizada. **Mitigación**: el checklist de PR incluye verificación de documentación de dominio.

### Límites de esta versión

- **Sin persistencia**: las entidades no se persisten en base de datos. No hay `DbContext`, migraciones ni repositorios implementados.
- **Sin servicios de aplicación**: las validaciones de transición de estados complejos (ej. ¿puede una mesa pasar de `Reservada` a `EnMantenimiento`?) no están implementadas; se manejarán en la capa de servicios de aplicación.
- **Sin interfaz de usuario**: esta versión no tiene páginas Razor para gestionar pedidos, productos o mesas. Es puramente dominio.

### Decisiones relevantes

| Decisión | Justificación |
|----------|---------------|
| **Domain-first sin persistencia** | Construir el modelo de dominio y verificarlo con pruebas antes de acoplarlo a una base de datos permite iterar más rápido sobre las reglas de negocio y evita que decisiones de infraestructura contaminen el dominio |
| **Nombres en español** | Refleja el lenguaje ubicuo del restaurante. Reduce la traducción mental entre dominio y código. Consistente con la convención del proyecto |
| **`ReglaDominioException` como base** | Todas las violaciones de negocio usan la misma excepción, facilitando el manejo centralizado en capas superiores y la trazabilidad en logs |
| **`IReadOnlyList` para colecciones** | Impide mutación externa de las líneas del pedido, obligando a usar `AgregarDetalle()` que ejecuta las validaciones de dominio |
| **Setters privados** | Ninguna propiedad puede ser modificada desde fuera de la entidad. Todo cambio de estado pasa por métodos con nombre de negocio que encapsulan las validaciones |
| **Enumeraciones para estados** | `EstadoMesa` y `EstadoPedido` modelan estados finitos del dominio. Evitan *magic strings* y permiten validación en tiempo de compilación |
